# AGENTS.md — secure-letter-signing

> **Roadmap:** `docs/ROADMAP.md` (v2) is the plan for the company platform (Django Ninja + Unfold server, Flutter app,
> per-brand deployments, E2E letters, per-device keys). The offline HTML app below is the legacy/fallback and the
> crypto reference. New platform code lives in `server/`, `app/`, `brands/`.

Offline app shipped as THREE self-contained HTML files in `dist/`: `employee.html` (admin team writes a letter, sends it
encrypted, verifies the signed reply, prints, edits & resends), `manager.html` (opens the letter, approves / requests
revision / rejects, signs) and `keygen.html` (makes `.private` + `.pub`). UI is Persian (RTL).

## Layout
- `src/crypto.js` — pure WebCrypto layer (no DOM). Source of truth for all security logic.
- `src/shared.js` — helpers + canvas letter renderer used by both pages.
- `src/employee.js`, `src/manager.js`, `src/keygen.js` — per-page logic. `src/layout.html` + `src/pages/*.html` + `src/style.css` — markup/CSS; markers `{{TITLE}} {{BODY}} /*STYLE*/ /*CRYPTO*/ /*SHARED*/ /*APP*/`.
- `build.mjs` — inlines everything into `dist/{keygen,manager,employee}.html` (the deliverables, no external deps).
- `test/crypto.test.mjs` — Node tests for the crypto layer.
- `docs/security.md` — threat model, file formats, revision flow. Update it when formats change.

## Commands
- `npm run build` → `dist/keygen.html`, `dist/manager.html`, `dist/employee.html`
- `npm test` → crypto tests (Node >= 19)
- Browser check: serve `dist/` (e.g. `python3 -m http.server`); pages share an origin, so a test can pass files between them via localStorage (set `<input type=file>` via DataTransfer, capture downloads by stubbing `HTMLAnchorElement.prototype.click`).

## Rules / gotchas
- Never add network calls, CDNs or external fonts: the app must work offline.
- Signature validity = ECDSA over canonical JSON of the whole payload. Any new field that
  matters must go inside `payload`, never beside it.
- Bump `V` in `crypto.js` and document it in `docs/security.md` on any format change.
- Private key never leaves `unlockIdentity`; keep `extractable:false` on imported keys.
- Wrap digits/hex in `ltr()` when drawing inside RTL canvas text, or they render reversed.
- `localStorage` may be unavailable; `store` degrades with a warning, keep it that way.
- Letterhead is copied into each letter (`letter.head`) so the manager's page needs no settings and the signed document is self-contained.
- Revision loop: letter `{id, no, rev, prevHash}`. Decision `revision` → employee clicks "ویرایش و ارسال مجدد" → `rev+1`, same `id`/`no`, `prevHash` = doc hash of the manager's signed reply.
- Print: `#printArea` must stay a direct child of `<body>` (in `layout.html`, not in a page fragment) because the print CSS hides every other body child. Wait for the image `load` event before `window.print()`; `img.decode()` never settles inside a `display:none` container.
- Styling: glass theme in `src/style.css` (CSS variables, light/dark via OS). Mobile-first; keep inputs at 16px (iOS zoom) and check there is no horizontal scroll at 375px.
- Palette (design tokens, do not invent new hues): Dark `#081528`/`#0F203A`, Gold `#BFA46F`/`#FBD57F`, Blue `#165EF6` (action) `#A4B9E4` (light) `#32568A` (mid), State `#4CD8B9` ok / `#D65959` error / `#CFA44B` warn, tints `#BBF0E4` / `#EFC9C9`. UI colours live as CSS variables in `src/style.css`; the white letter paper uses the `PAPER` object in `src/shared.js` (darker shades of the same hues for contrast on white).
- Font: Vazirmatn (SIL OFL, `src/fonts/`, license in `OFL.txt`) is inlined as base64 `@font-face` by `build.mjs` (`/*FONT*/` marker in `style.css`), so pages stay offline. Canvas text must `await document.fonts.load(...)` before measuring (done in `renderLetter`).
- Layout: pages use `.split` > `.seg` (phone switch) + `.pane` cards. Phone shows one `.pane.active` at a time (`setPane(id, name)` in `shared.js`); ≥900px shows all panes side by side with the preview pane `.sticky` (scrolls inside itself). Keep each phone screen about one viewport tall; move content between panes rather than stacking cards. Scope tab handlers to `[data-tab]` so they never catch `.seg` buttons.
- Manager page: row 1 = collapsible `<details id="keySetup">` (open while locked, auto-collapses on unlock, summary shows the signer); row 2 = `.split` with letter pane + decision/sign pane. Employee page uses the same `<details>` pattern for its setup block.

## Platform (Phase 0+)
- `server/` Django 6 + django-ninja (API) + unfold (admin). `uv sync`, `DJANGO_DEBUG=1 uv run pytest`. Env-driven settings (`BRAND`, `DJANGO_SECRET_KEY`, `POSTGRES_*`); no secret → refuses to start unless `DJANGO_DEBUG=1`.
- `brands/<id>/brand.json` + `logo.svg` + `.env` (git-ignored; template `brands/.env.example`). One company per deployment.
- `./build.sh <brand> up` → docker compose (db, redis, server). `./build.sh <brand> app <apk|ios|macos|windows>` → copies brand into `app/assets/brand/` (git-ignored, generated) and runs `flutter build --dart-define=BRAND=<id>`. Before local `flutter test/run`, copy `brands/demo/*` into `app/assets/brand/`.
- `app/` Flutter (Android, iOS, macOS, Windows; no web). `app/lib/crypto/letter_crypto.dart` is the Dart port of `src/crypto.js` using pointycastle (the `cryptography` pkg has no pure-Dart ECDSA).
- **Crypto contract:** the JS/HTML legacy app keeps its own vectors (`test-vectors/v1.json`, `node test-vectors/make.mjs`); the platform no longer shares crypto with it (server seals with Ed25519, see `docs/signing-v3.md`).
- `make dev` (port 8090 via `PORT=`; SQLite + in-memory channel layer/celery, no Docker, auto-reload), `make macos` (runs the macOS app against it; start `make dev` first), `make up|down|logs` (Docker, `BRAND=<id>`), `make test`, `make app`, `make superuser`. Redis is used only when `REDIS_URL` is set (compose sets it).
- Docker stack was written but not yet run end to end (Phase 0 gap: needs a running Docker daemon).

## Server apps (Phase 1)
- `accounts/`: custom email `User` (`is_manager` = the single manager, partial unique constraint; set only by the superuser in the Unfold admin), `Permission` catalog (seeded: user, letter.create, letter.see, letter.sign; user M2M is `grants`), `Session`, `InviteCode`, `CompanySettings` (singleton; signup switches + SMTP), `AuditEvent` (no hash chain yet, Phase 5).
- Tokens are opaque `django.core.signing` access tokens (10 min) + rotating refresh tokens; every request also checks the `Session` row, so revoke is immediate. Refresh reuse revokes the session. (Roadmap said JWT; this is simpler and instantly revocable.)
- API: `/api/auth/*` (signup, verify-email, login, refresh, logout, password-reset), `/api/me/*` (profile, sessions, revoke, password), `/api/manage/*` (manager only: users, permissions, company, invites). Domain signup needs email configured (verification token by mail) else 503; invite signup needs no email.
- No deletion anywhere: deactivate/revoke/unlist. Admin classes block delete. Superuser admin must never register letter models.
- Email goes through `accounts/mailer.py` using SMTP from `CompanySettings`; Django 6.1 deprecates `EMAIL_BACKEND`/`get_connection` (removed in 2028): migrate to `MAILERS`.
- Phase 1 reviews done (security + Django); fixes applied. Hardening: per-email login/reset/`/me/password` lockout (`accounts/ratelimit.py`, 10 failures/15 min, cache-backed); Redis `CACHES` when `REDIS_URL` set (throttles shared across workers); `NUM_PROXIES` (default 0 = ignore X-Forwarded-For) drives client IP; refresh tokens: every rotated token is kept in `RetiredRefresh`, reuse of any retired token revokes the session, except the immediate predecessor within 10 s (lost-response retry gets a fresh pair); `Cache-Control: no-store` on `/api/`; prod settings (HTTPS redirect, HSTS, secure cookies) unless `DJANGO_HTTPS=0` (compose default 0).
- **Known gaps:** mail is sent synchronously (use `on_commit` + Celery; also makes reset latency uniform); `smtp_password` plaintext; HSTS subdomains/preload not set; `MAILERS` migration pending.
- Flutter Phase 1: `app/lib/api/` (`ApiClient` auto-refresh single-flight, refresh token in `flutter_secure_storage`, access token memory-only; `AuthController`), `app/lib/screens/` (login, signup, reset, profile, devices, manager admin tab). Not yet run on a device.

## Server apps (Phases 2-5)
- `letters/`: `Letter` (title plaintext; `body` column = `{"v":3,"ct":<Fernet token>}`, encrypted/decrypted by the API via `core/cryptoutil.py`), `Participant` (signer/viewer; `role="removed"` rows are soft-dropped draft people), `Signature` (immutable; `payload`, Ed25519 `seal`, `method` pin|biometric), `SignRequest` (remote biometric approval; DELETE blocked, UPDATE allowed), `Attachment` (Fernet-encrypted file on `MEDIA_ROOT`), `LetterEvent` (catch-up cursor). Rules live in `letters/rules.py` (visibility, audience). State: draft -> in_signing -> published | rejected | cancelled, plus `unlisted` (manager, published only). Sent letters are immutable; `shown_at` = when viewers may see it. Signing logic is in `letters/signing.py` (turn check, PIN check, seal, advance) and `letters/sign_requests.py` (router `/sign-requests`). Full contract: `docs/signing-v3.md`.
- **Signature contract (v3):** server-side crypto, no client keys. Secrets: `DJANGO_DATA_KEY` (Fernet at rest) and `DJANGO_SEAL_SEED` (Ed25519 seal), both HKDF-derived in `core/cryptoutil.py`, required unless `DJANGO_DEBUG=1`; losing/changing DATA_KEY makes stored letters unreadable, changing SEAL_SEED invalidates old seals. A signer proves identity by signing PIN (`POST /letters/{id}/sign`, `User.signing_pin_hash`, 5 failures/15 min -> 429, scope `sign-pin`), biometric session (`sign-biometric`, `Session.biometric`), or remote approval by another biometric session (`/sign-requests`, 5 min expiry; expiry is derived on read, not persisted). Payload `{v:3,letterId,title,decision,note,contentHash,parentId,signer{userId,email,name},method,sessionId,deviceName,signedAt,nonce}`; `contentHash` = sha256 of canonical JSON of the PLAINTEXT body; `seal` = Ed25519 over canonical payload, public key at `GET /letters/seal-key`; `/certificate` re-verifies seal and hash. Limitation: the server cannot verify that a biometric check really happened (no device-bound key); it trusts the session flag. Login ignores `biometric` (new sessions are always `biometric=false`); turning it on needs the signing PIN via `PATCH /me/sessions/current {biometric, pin}` (same `check_pin` path and counters as signing, audit `session_biometric_enabled`; off needs nothing).
- Live: `/ws/?token=<access>` (`letters/consumers.py`; joins groups `user_<id>` and `session_<sessionId>`; `sign_request` / `sign_request_update` frames are session-targeted and not replayed), events also stored in `LetterEvent`; client sends `{"after": id}` to catch up. Notifications: `accounts/notify.py` stores `Notification`, pushes over WS, emails when SMTP/email is configured. In-app list: `/api/me/notifications`.
- Audit: hash chain (`accounts/models.py: audit()`, `verify_audit_chain()`, `manage.py verify_audit`); Unfold shows chain status and CSV export. Never put letter titles in audit data (superuser reads it). DB triggers (`letters/migrations/0002`) refuse DELETE on all records and UPDATE on audit/signatures/events; never use `transaction=True` pytest tests (flush deletes) and use `django_capture_on_commit_callbacks(execute=True)` when a test needs `on_commit` hooks.
- Ops: `scripts/backup.sh`, `scripts/restore.sh`, `docs/RELEASE.md`.
- Security review of Phases 2-5 applied (drafts private to creator, `parentId` signed, size caps, HMAC audit chain keyed by SECRET_KEY, sent letters immutable at DB level). **Open:** attachments are not bound into the signature (put attachment ids + ciphertext hashes inside the encrypted body), no per-user upload quota (also set `client_max_body_size` at the proxy), WebSocket token is in the query string (keep it out of access logs), `no` assignment is max+1 without a lock, record `verify_audit`'s head hash off-database to detect deleted tail rows, run Postgres as a non-owner role.

## Server apps (workspace, platform phase 1)
- `server/workspace/` (design: `docs/platform-design.md`): `Subject` anchor plus `Label`/`SubjectLabel`, `File`, `Comment`, `ChangeHistory`, `SeenBy`, `Event`/`EventRecipient`, `Reminder` (the last five have models only, no endpoints yet). Module apps register a `ModuleSpec(code, router, resolve, can)` from `AppConfig.ready()` (`workspace/registry.py`); shared endpoints (`PUT /subjects/{id}/labels`) never decide access, they call `spec.can(user, obj, "see"|"label")` (404 invisible, 403 not allowed) after `require_module`. `brand.json` optional `"modules"` list (default all) drives `enabled_modules()` and `GET /me/modules`.
- Workspace live stream: `workspace.events.emit(module, kind, subject, title, actor, recipient_ids, **data)` stores Event + EventRecipient and pushes `{"type":"ws","stream":"w",...}` on commit to recipients only; replay via `GET /events/w` or `{"after_w": n}` on the WebSocket (`{"after": n}` is still the letter cursor).
- `core/dbguards.py` `guard(tables, no_update=[...])` is the migration helper for append-only triggers (workspace migration 0002 uses it; letters 0002 is untouched). `core/filestore.py` `save_encrypted/read_decrypted` wrap Fernet file IO (letters attachments use it). New users (signup, invite, CSV import) get `accounts.models.DEFAULT_GRANTS` (`user`, `task.create`, `project.create`); workspace migration 0003 granted the two new ones to existing users. Tests that need a module register a dummy one (`workspace/tests/conftest.py`).
- **Tasks (platform phase 3) and subject collaboration (phase 4):** `server/tasks/` (router `/api/tasks`, registered from `TasksConfig.ready()` via `tasks/module.py`): `Task` (one `workspace.Subject`, description encrypted `{"v":3,"ct"}`, titles plaintext, `version` for optimistic PATCH, 409 on mismatch), `TaskPerson` (owner/approver/follower; approvers decide serially by `position`; removed people are deactivated), `ChecklistItem`. `project`/`column` are real nullable PROTECT FKs to `projects` (tasks migration 0003). Rules in `tasks/rules.py` (`denial()` gives 403 for role, 409 for wrong state; manager gets no access), state machine in `tasks/workflow.py` (complete -> awaiting_approval|done, reject -> open with the note as a report comment, reopen/cancel creator only), field/people edits in `tasks/service.py`, checklist in `tasks/checklist.py`, boxes/filters in `tasks/queries.py`. Every change writes `ChangeHistory` (encrypted fields `{"changed":true}`), emits `task.*` events to creator + active people minus the actor, notifies newly added people and the next approver; audit rows (create/complete/decision/cancel/reopen) carry ids only.
- Phase 4 generic endpoints (`workspace/api_subjects.py`; comments in `workspace/comments.py`, files in `workspace/files.py`): comments/files/history/seen on any subject, all gated by `registry.can` (404 invisible, 403 not allowed). `ModuleSpec` gained optional `audience(obj)` (recipients of `comment.created`/`file.added`) and `set_progress(obj, user, value)` (a `report` comment with progress needs `can(...,"progress")` else 403, and modules without it refuse reports with 422). Actions used: see, comment (also needed to post comments/files), label, progress, moderate (delete others' comments/files; tasks: the creator). Comment edit = replacing row (same `created_at`, replies re-pointed, old row inactive); delete only deactivates. Files: same type/size limits as letter attachments (`core.filestore.ATTACHMENT_TYPES`), max 20 active per subject, `sha256_plain` verified on download.
- **Projects (platform phase 5):** `server/projects/` (routers `/api/projects`, `/api/project-groups`): `ProjectGroup`, `Project` (own Subject, module `projects`, description encrypted, `progress` cached by `projects/progress.py` = rounded average of non-cancelled task progress, refreshed from `tasks.store.save` and on create/move), `ProjectMember` (manager|member|viewer, owner = always a manager row, removal = `active=False`), `BoardColumn` (todo|doing|done kinds; default To do/Doing/Done at creation). Rules: `projects/rules.py` (see/comment any member, label/create_task manager+member, edit/moderate manager); `projects/membership.py` is what `tasks/rules.py` imports (no tasks import there). Project tasks are visible to every active project member only (`tasks/queries.visible_tasks`, `rules.audience` = members); everyone on a project task must be a member (422 otherwise). Moving/copying: `tasks/placement.py` (rank gaps 65,536, midpoint insert, renumber under `select_for_update` on the column; action `move` = creator or project manager, no state rule; moving to a done-kind column does not complete) and `tasks/copying.py` (new subject, same people/checklist/labels, File rows share blobs, people not in the target project are dropped, the copier owns it if no owner is left). `GET /projects/{id}/tasks?view=board|list|calendar`. Events `project.created|updated|member.added`, `task.moved`; notifications `project.member_added`. Migrations guard the projects tables and re-create the tasks_task trigger after the SQLite rebuild.

## Server apps (meetings, notes, polls)
- `server/meetings/` (router `/api/meetings`, `/api/meeting-templates`): `Meeting` (Subject module `meetings`, description encrypted, `revision` bumped by reopen), `MeetingAttendee` (chair|secretary|member|guest, external guests have `guest_name` and no user), `Resolution` + `ResolutionOwner`, `MeetingMinutesSignature` (immutable: DB refuses UPDATE/DELETE; sealed like letter signatures via `letters.signing.check_pin` + `core.cryptoutil`, payload binds meetingId, revision, contentHash of description+resolutions+attendance), `MeetingTemplate`. Anonymity is enforced in `polls/results.py` (voter lists and per-person quiz scores are never computed for callers who may not see them). `anonymous_to_all` still stores `user` on answers (DB admins can see it).

- **CRM (customer files):** `server/crm/` (router `/api/customers`, module `crm`): `Customer` (own Subject; name/phone/mobile/email/national_id plaintext, address/notes encrypted), `CustomerMember` (manager|member|viewer; creator = owner = manager; only members see anything, the company manager gets nothing; `crm/rules.py`, `crm/membership.py` is what tasks/meetings/letters import), append-only `CustomerEvent` timeline (`crm.timeline.record(customer, kind, summary, by, ref_subject)` is the service other apps call; encrypted summary) and `CallReport`. `tasks.Task.customer` and `meetings.Meeting.customer` are nullable PROTECT FKs (link needs manager/member on the file, tasks also `task.create`; briefs expose `customer_id/customer_name` only to members of that file). Letters keep `CustomerLink.customer_ref` (bare UUID): `letters.secretariat.set_customers` now validates new refs against files the caller is a member of (422) and keeps links the caller cannot see. `crm/signals.py` writes timeline rows when a linked task/meeting/letter changes status. `CUSTOMER_LIMIT` setting (default 10000, all statuses counted, 409 beyond). Import: `crm/imports.py` (CSV or xlsx, permission `customer.import`, granted to nobody); `core/xlsx.py` is a zip+XML reader (no openpyxl). `customer.create` is in `DEFAULT_GRANTS`. Details: `docs/platform-design.md` "Implemented: crm".
- **Finance and sales (server):** `server/finance/` (module `finance`, permission `finance.manage`) and `server/sales/` (module `sales`, permission `sales.manage`); both permissions are seeded by their own migration 0002 and granted to nobody (the company manager grants them). Every route of both is 404 for non-holders and when the module is off (`service.gate`). `FinanceDoc` / `Lead` own a Subject (labels, files, comments via the generic `/subjects/*` endpoints, `rules.can` decides), amounts/values/dates/probability are plaintext (aggregated), descriptions and void/lost reasons are encrypted, status changes (void, win/lose/reopen) write `ChangeHistory` through `workspace/changes.py` (secret fields record `{"changed":true}`), audit rows carry ids only, DB triggers refuse DELETE. A document or lead linked to a customer also needs membership of that file (any role); customer timeline rows (kind finance|lead) never contain amounts or titles because every member reads them. Reports use `workspace/periods.py` (Gregorian or Jalali month/year buckets, gaps filled) and `finance/reports.py` (void never counts; pending docs sit at their due date). `SALES_SHARED_VISIBILITY` (settings/env, default on) lets all holders see every lead; off = owner/creator only. Details: `docs/platform-design.md` "Implemented: finance and sales".
