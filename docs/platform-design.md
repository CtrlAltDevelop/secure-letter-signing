# Workplace suite: shared core, tasks and projects

Letters are one module of a Persian (RTL, Jalali) workplace-automation suite. Decisions: shared core first, then tasks and
projects; Flutter Web added to the same app; every module enabled for now (the "advanced" set) with a seam for plan gating.
Rules that still hold: server-side crypto, one deployment per company, no hard deletes (deactivate/archive), append-only DB
triggers, HMAC audit chain (never put task/project titles in audit data), signing per `docs/signing-v3.md`.

## Server architecture
- New Django app **`workspace`** (not `platform`: stdlib clash). Shared models, module registry, generic routes. `core` stays
  model-free. Module apps: `tasks`, `projects`, later `chat`, `meetings`, `crm`. Each has models, rules.py (visibility, like
  `letters/rules.py`), api.py, events.py.
- `workspace/registry.py`: `ModuleSpec(code, router, resolve(subject)->obj, can(user, obj, action)->bool)` registered in each
  app's `AppConfig.ready()`. `enabled_modules()` reads `brand.json` `"modules"` (default all). `require_module(code)` -> 404
  when off. `GET /api/me/modules`. Plan gating later = one map plan->modules inside `enabled_modules()`.
- Permissions: reuse `accounts.Permission`/`User.grants`; seed `task.create`, `project.create` (data migration, grant to all
  existing users). Visibility comes from membership rows; the manager gets no automatic access to content. Shared endpoints
  never decide access themselves: they call `registry.get(subject.module).can(...)`.
- Generalise: live events through new `workspace.Event`/`EventRecipient` (recipients computed at write time; WebSocket frames
  carry `"stream":"w"`; consumer accepts `{"after": n, "after_w": m}`; letters keep `LetterEvent` unchanged). Notifications:
  keep `accounts.notify.notify()` (add `module`, `subject_id`, `object_id` inside `data`). Move encrypted file read/write from
  `letters/api.py` into `core/filestore.py` (`save_encrypted`, `read_decrypted`); copy the no-delete trigger SQL into
  `core/dbguards.py` (`guard(tables, no_update=[...])`) for new migrations. Leave alone: Letter/Participant/Signature/
  SignRequest/letters.Attachment, signing code, LetterEvent replay, migration 0002.

## Shared core models (`workspace`), anchored on `Subject`
Every entity that carries comments/files/labels has `subject = OneToOneField(Subject, PROTECT)`; shared tables FK to Subject.
1. `Subject(id uuid, module, kind, created_at)`.
2. `Label(id, scope org|personal, owner null, name, color smallint, active)` unique (owner, name); `SubjectLabel(subject, label,
   added_by, at, active)` unique (subject, label). Removing = `active=False`.
3. `File(id uuid, subject, uploaded_by, name, content_type, size, sha256_plain, blob Fernet-encrypted, active, created_at)`.
4. `Comment(id, subject, author, parent null (one reply level), kind comment|report, body encrypted, progress_snapshot null,
   replaces null, active, created_at)`; append-only (edit = new row with `replaces`).
5. `ChangeHistory(subject, actor, field, old JSON, new JSON, at)`, no UPDATE; encrypted fields record `{"changed":true}`.
6. `SeenBy(subject, user, first_at, last_at)` unique.
7. `Event(id, module, kind, subject null, title, actor, data JSON, at)` + `EventRecipient(event, user)`; no UPDATE.
8. `Reminder(id, subject, user, created_by, next_at, rule JSON null, active, last_fired_at)`; `rule = {freq: daily|weekly|
   monthly_jalali, interval, weekdays, day}`, `next_at` via `jdatetime` in Asia/Tehran; `fire_due_reminders` every minute
   (`select_for_update(skip_locked=True)` then `notify()`); dev: `manage.py run_reminders`.
Content at rest: titles/names plaintext (searchable), descriptions/comments/files encrypted.

## Projects and tasks
`projects`: `ProjectGroup(id, name, owner null, rank, active)`; `Project(id uuid, subject, name, description enc, group null,
color, status active|done|archived, owner, start_date, end_date, progress cached, created_at)`; `ProjectMember(project, user,
role manager|member|viewer, active, added_by, at)` unique (project, user); `BoardColumn(id, project, title, rank BigInt,
kind todo|doing|done, active)`.
`tasks`: `Task(id uuid, subject, project null, column null, rank BigInt, title, description enc, creator, status open|
awaiting_approval|done|cancelled, priority low|normal|high|urgent, start_at, due_at, all_day, progress 0-100, progress_mode
manual|checklist, version int, copied_from null, completed_at, created_at, updated_at)`; `TaskPerson(task, user, role owner|
approver|follower, position, decision ''|approved|rejected, decided_at, active)` unique (task, user, role);
`ChecklistItem(task, text, done, done_by, done_at, rank, active)`. Ranks: gaps of 65,536, renumber under `select_for_update`.
Rules: see a task = every active project member (if in a project) else creator + active TaskPerson. Edit project/columns/
members: manager or owner. Create task in project: manager/member (not viewer) with `task.create`. Edit fields/people/cancel:
creator or project manager. Progress/checklist/reports/complete: owners. Approve/reject: current approver (serial by
position). Comment: anyone who can see. Move: edit rights in source + member rights in target. Copy: visibility of source +
create rights in target; copy gets new subject, same people/checklist/labels, no comments/history, File rows share blobs.
Completion: owner completes -> `awaiting_approval` if approvers else `done`; rejection -> `open` with the note as a report
comment. No task/project models in Unfold admin.

## Implemented: phases 5 and 6 (server) - deviations
- Everyone on a project task (owners, approvers, followers) must be an active project member (422), because project tasks are visible to members only; copy drops non-member people instead (the copier owns it when no owner is left). Moves into a project fail with 422 for the same reason.
- New task action `move` (creator or project manager, no state rule) so finished tasks can still be dragged; `PATCH /tasks/{id}` with a changed `project_id` performs a move (default column). `TaskIn` gained `column_id`; `TaskBrief` gained `column_id` and `rank`; `can.move`.
- Archived projects refuse new tasks, moves and copies into them (409). Hiding a column needs it to be empty and not the last one (409). Project views are capped at 1000 tasks; `list` is ordered by due date then rank.
- `PUT /projects/{id}/members` takes the bare list as body and returns `ProjectOut`; an owner missing from the list or demoted is 422. Column endpoints return the column list. Personal groups are private: other members see `group_id: null`.
- Reminders: `at` must be in the future and carry an offset; `GET` lists only the caller's active reminders; the stored rule is completed with defaults (`weekdays`, `day`). `jdatetime` was not available offline, so `workspace/jalali.py` is an own port of the jalaali-js algorithm (tested against 1405-01-01 = 2026-03-21, leap years 1403/1408, 60-year round trip). Missed recurrences are not replayed (one notification, next occurrence after now). Reminders of users who lost access or of disabled modules are deactivated silently. No Celery app exists in the repo, so no beat entry; use `manage.py run_reminders`.
- `select_for_update` is a no-op on SQLite: rank/reminder races are untested here (need Postgres in CI).


## Implemented: letters v2 (server) - deviations
- Letters are workspace subjects (`Letter.subject`, nullable one-to-one, data migration 0005 fills old letters); the 'letters' `ModuleSpec` also resolves secretariat entries (subject kind `secretariat_entry`, visible to `letter.secretariat` holders only). Letter actions: see/comment/label = `can_see`, moderate = creator. Letter attachments, signing and `LetterEvent` are untouched; new features emit only workspace events (`letter.referred|referral_responded|task_linked|task_unlinked|paraphed|numbered`, `secretariat.registered`), ids only.
- SQLite rebuilds `letters_letter` for the new one-to-one and drops its triggers: migration 0006 re-creates them.
- Boxes: outbox and inbox both exclude letters the caller archived; `box` defaults to `all` (old behaviour). Any referral row (pending, done or declined) keeps read access; an unlisted letter hides from referees like from viewers. Referral targets already pending are skipped silently. Drafts and cancelled letters cannot be referred.
- Paraph: only signers, viewers and referees (not the creator, not public readers) on in_signing/published letters. The certificate adds `paraphs` and `paraphs_verified`; a paraph verifies only if seal, `kind`, `letterId`, content hash and signer id all match.
- Secretariat: outgoing numbers need a published letter the clerk can see (so a private letter must list the clerk as viewer); `in` entries cannot point to a letter. One `CustomerLink` table keyed on Subject serves letters and entries (nullable `customer_ref`, no FK). `PUT /letters/{id}/customers`: creator or secretariat holder who can see the letter.
- Search covers titles, numbers, participants, labels, secretariat data and decrypted body text of only the most recent 500 visible letters not already matched on metadata.
- `GET /letters` stays in `api.py` (a second router cannot share the `""` path); other new routes live in `api_inbox/api_referrals/api_links/api_secretariat`, `/referrals` and `/secretariat` are mounted via `api_v2.py`.

## Implemented: crm (server)
Module `crm` (in `KNOWN_MODULES` and `brands/demo/brand.json`), router `/api/customers`. Errors: 403 role, 404 invisible (non-members, including the company manager), 409 limit/archived, 422 validation. Labels, files, comments, seen and reminders use the generic `/subjects/{subject_id}/...` endpoints (viewers may comment/upload; label needs manager/member).

`CustomerBrief={id,subject_id,kind:person|company,name,legal_name,national_id,phone,mobile,email,status:active|inactive|archived,owner_id,my_role,label_ids,unseen,updated_at}`; `CustomerOut` = Brief + `registration_no`, `address:{text}`, `notes:{text}`, `owner:UserRef`, `members:[{user:UserRef,role}]`, `can:{see,comment,label,link,event,call,edit,members}`, `created_at`.
- `POST /customers` `{kind?,name,legal_name?,national_id?,registration_no?,phone?,mobile?,email?,address?:{text},notes?:{text},status?,members?:[{user_id,role}]}` -> 201 CustomerOut (needs `customer.create`; 409 `Customer limit reached` at `CUSTOMER_LIMIT`). `GET /customers?q=&status=a,b&kind=&label=&mine=&limit=&offset=` -> `[CustomerBrief]` (members only, ordered by name; `q` matches name, legal_name, phone, mobile, email, national_id; `mine` = I own it). `GET|PATCH /customers/{id}` (PATCH = manager only; fields present change, `null` clears text; owner cannot be changed). `PUT /customers/{id}/members` bare list `[{user_id,role}]` -> CustomerOut (manager; owner must stay manager).
- `GET /customers/{id}/history` -> same rows as `/subjects/{subject_id}/history` (every changed field; `address`/`notes` record `{"changed":true}`; `members` and, on tasks/meetings, `customer` are recorded too).
- Timeline: `GET /customers/{id}/events?kind=&limit=&offset=` -> `[{id,kind,summary,at,by:UserRef|null,ref_subject_id}]` newest first; `POST` `{kind:note|call|meeting|finance|lead (default note),summary,at?}` -> 201 (manager/member). `system|task|letter` rows come from code only (`crm.timeline.record`, links, `crm/signals.py` on status changes; `by` is null for signal rows). DB refuses UPDATE and DELETE on events and call reports.
- Calls: `POST /customers/{id}/calls` `{direction:in|out,contact_name?,summary?,at?,duration_s?}` -> 201 `{id,direction,contact_name,summary,at,duration_s,by}` (also a timeline `call` row); `GET` lists. `POST .../calls/{cid}/to-task` `{title?,owner_ids?,due_at?}` -> 201 TaskBrief (title default `Follow up: <contact or customer>`, description = call summary; needs `task.create`; linked to the customer; timeline `task` row).
- Links: `TaskIn/TaskPatch`, `MeetingIn/MeetingPatch` accept `customer_id` (null unlinks); `TaskBrief/MeetingBrief` gain `customer_id`, `customer_name` (null unless the caller is a member of the file). `GET /tasks?customer=<id>`, `GET /meetings?customer=<id>`, `GET /customers/{id}/tasks|meetings|letters` list only what the caller can see (letters as `LetterBrief`). `PUT /letters/{id}/customers` and `/secretariat/entries/{id}/customers`: newly added refs must be files the caller is a member of (any role) else 422; refs the caller cannot see are kept untouched; a `letter` timeline row is written for each new link.
- Import: `POST /customers/import` multipart `format=csv|xlsx`, `file` (headers `kind,name,legal_name,national_id,phone,mobile,email,address,status`; only `name` required) -> `{created,skipped,errors:[{row,message}]}` (`row` = sheet row, header = 1). Existing or repeated national_id/email are skipped; invalid rows are errors; beyond the limit rows are errors. 413 over 5 MB, 422 over 5000 rows, bad header/encoding/format. Needs `customer.import` (seeded, granted to nobody). The importer becomes owner/manager of each file.
- Events: `customer.created|updated|member.added` (to members minus the actor), notification `customer.member_added`. Migrations: crm 0001 (tables + append-only guards), 0002 (permissions `customer.create` granted to existing users, `customer.import`), tasks 0005 and meetings 0003 add the FK and re-create the SQLite triggers.
Deviations: no `File.category` (documents are plain files; put the kind in the file name); `CUSTOMER_LIMIT` is read from the environment; viewers cannot link or add notes/calls; copying a task drops its customer link; customer owner transfer is not implemented because `ModuleSpec.transfer` does not exist yet (TODO: move ownership and membership rows when it lands); a `crm` module switched off refuses new task and meeting links (404) and letter links (422) while existing ones stay.


## Implemented: finance and sales (server)
Modules `finance` and `sales` (in `KNOWN_MODULES` and `brands/demo/brand.json`), routers mounted at `""` (`/api/finance/*`, `/api/sales/*`, `/api/customers/{id}/finance|leads`). Both return briefs of ACTIVE (`open` / `awaiting_approval`, not hidden) tasks only: the team calendar returns `CalendarItem`s with `owner_ids` (kinds other than tasks are ignored; `user` = owner filter), `tasks/of` returns `TaskBrief`s computed with the target's boxes (`inbox` = what they must do, `followup` = what they created or follow) with the viewer-relative fields blanked (`my_roles: []`, `label_ids: []`). No description, comment, file, checklist text, chat or letter body is ever included, and the normal detail endpoints stay 404 for the holder. Anyone else gets 403 (including the company manager).
- **Holidays** `Holiday(date, title, kind official|religious|company, active)` unique per (date, title). `GET /holidays?from=YYYY-MM-DD&to=YYYY-MM-DD[&include_inactive=true]` (any user; `include_inactive` only honoured for the manager; range max 800 days) -> `[{id, date, title, kind, active}]`; `POST /holidays {date, title, kind="company"}` (manager) -> 201 (an existing inactive row is reactivated, an active duplicate is 409); `PATCH /holidays/{id} {date?, title?, kind?, active?}` (manager; deactivating is the delete). `manage.py load_holidays --from-year 1405 --to-year 1410` seeds the fixed Jalali official days (1-4 Farvardin, 12 and 13 Farvardin, 14 and 15 Khordad, 22 Bahman, 29 Esfand; idempotent; at most 60 years); lunar days are entered by the manager. The calendar response carries the active holidays of the Tehran days covered by the range; `weekend` is the constant `[5]` (Friday).

**Unified search** `GET /search?q=&modules=a,b&limit=20` (q at least 2 characters else 422; limit 1-50; 60 requests per minute per user else 429 via `accounts.ratelimit.hit(window=60)`) -> `[{module, kind, id, subject_id, title, snippet, at}]`. New optional `ModuleSpec.search(user, q, limit) -> list[dict]` (helper `workspace.search.hit`); modules that are off, or that raise, are skipped. Merge: every module with hits gets an equal share first, leftovers fill in registration order; the result is grouped by module in registration order, never re-sorted. Per module (identifying fields only): tasks (title, the caller's label names; snippet = status), projects (name), letters (title, number, participants, labels via `letters.inbox.metadata_search`; snippet = number; bodies are NOT scanned), meetings (title), crm (name, legal name, phone, mobile, email, national id; snippet = the matching contact value), notes (own titles), finance (`finance.manage` holders: customer name, amount, description text within the latest 500 visible docs; title = `"<direction> <amount>"`, snippet = customer name), sales (`sales.manage` holders: lead title, customer name, value), chat (conversation names, plus message text of the latest 1000 messages across the caller's conversations; `kind` conversation|message, snippet 80 chars around the match; implemented in `chat/unified.py` and wired in `chat/module.py`). Pseudo-module `files` (always on): workspace `File` names, only for files whose subject passes the module's `can(.., "see")` (200 newest candidates; `snippet` = the owning object's title). Amounts accept Persian/Arabic digits and thousand separators.

**Bookmarks** `Bookmark(user, target_module, target_id, subject, title, note (encrypted), created_at, active)` unique (user, target_module, target_id). `GET /bookmarks?module=` -> `[{id, module, kind, target_id, subject_id, object_id, title, note, created_at}]` newest first (re-checked on every read: targets the caller lost access to, and switched-off modules, are skipped but kept); `PUT /bookmarks {module, id, note?}` -> 200 same shape (idempotent; reactivates a deactivated row; `note` absent keeps the old note, `""` clears it); `DELETE /bookmarks/{id}` -> 204 (own rows, deactivates). For subject-backed modules (tasks, letters, anything with a Subject) `id` may be the subject id OR the module object id; it is normalised to the subject id in `target_id` (`object_id` = the module object id). Visibility is `registry.resolve` + `can(.., "see")`, else 404. Targets without a subject (chat messages: `id` = message id) are verified by the new optional `ModuleSpec.bookmark_check(user, target_id) -> title | None` (chat: active member of the conversation, message not deleted; title = the conversation name, never message text); a non-subject module without that hook is refused (404; deviation: the brief said to trust chat without a hook). Max 1000 active bookmarks (422).
**Pins** `Pin(user, subject, rank, active)` for modules `projects`, `crm` (customer files) and `chat` (conversations) only (other subjects 422), validated with `can(.., "see")` (404). `GET /pins` -> `[{subject_id, module, kind, title}]` by rank (lost access or module off: skipped); `PUT /pins {subject_id}` -> 200 the new list (idempotent, appended at the end, max 50); `DELETE /pins/{subject_id}` -> 204 (deactivates).

**Preferences** `accounts.UserPrefs` (created lazily), `GET/PATCH /me/prefs` -> `{theme: light|dark|auto, birthday: date|null, birthday_visible: true, dnd_until: datetime|null, personal_email, personal_email_verified, has_background}`; PATCH takes `theme`, `birthday` (`null` clears; not in the future), `birthday_visible`, `dnd_until` (`null` clears).
- Personal email: `POST /me/personal-email {email}` (rate limited 5 per 15 min; 503 when email is not configured, 422 invalid) stores the address unverified and mails a signed token (24 h, bound to user and address, so a newer address invalidates the old token); `POST /me/personal-email/verify {token}` -> prefs (400 invalid/expired, 10 tries per 15 min). `accounts.notify.notify` keeps mailing every notification to the account email, and now also mails kinds in `notify.IMPORTANT_KINDS` (task.assigned, task.approval_needed, meeting.invited, letter_published, letter_rejected, letter_referral, referral_response, sign_request, mention, reminder, work.transferred, lead.assigned, task.removal_requested) to a VERIFIED personal address.
- Do not disturb: while `dnd_until` is in the future at delivery time (after commit) the `Notification` row is still stored but the WebSocket push and every email (account and personal) are skipped.
- Background image: `POST /me/background` multipart `file` (png, jpeg, webp by content sniffing, not by name or declared type; max 2 MB, 413/422) -> prefs, stored Fernet-encrypted (`core.filestore`); `GET /me/background` -> decrypted bytes with the sniffed content type (404 when none); `DELETE /me/background` -> 204 (deactivates; the file is kept; a new upload replaces it).
- Birthdays and the daily run: `accounts.DailyRun(name, date)` unique guard row (Asia/Tehran date; claim and job run in one transaction so a failing job is retried); `accounts/daily.py` `run_pending()` is called by `manage.py run_daily` and on every `run_reminders` tick (cost: one lookup per job after the first run of the day). Job `birthdays`: every active colleague except the person gets notification kind `birthday` (title = the person's name, `data = {user_id}`) when the person set a birthday and `birthday_visible` is true. Deviation: the birthday is matched by its JALALI month and day (30 Esfand is celebrated on 29 Esfand in common years), because users think in Jalali dates; the stored value is the Gregorian date.

**Done list** `GET /tasks/done-daily?date=YYYY-MM-DD` (default: today in Asia/Tehran; bad date 422) -> `{date, total, groups: {completed, submitted, approved, rejected}}`, each item `{task_id, subject_id, title, project_id, project_name, at}` in time order. Built from the task history rows where the caller was the actor that Tehran-local day: `completed` (status to done: an owner completing without approvers, or the last approver), `submitted` (status to awaiting_approval), `approved` / `rejected` (the caller's decisions); tasks the caller can no longer see are skipped. Rows come from append-only history, so reopened and re-completed tasks appear every time.

**Transfer hooks** (`POST /users/{id}/transfer` response gains `crm` and `sales` counts, besides `chat`, `chat_pins`): `crm` moves every active file membership of the source to the target keeping the role (the owner becomes owner of the file and manager); a target that already has the same or a higher role keeps it and the file does not count as moved; the source membership ends either way. `sales` moves OPEN leads whose owner or creator is the source (owner and `created_by` become the target; history rows `owner` / `created_by`), only when the target holds `sales.manage`, and a lead linked to a customer file only when the target is a member of it (CRM runs first, so file memberships have already moved). No notification per lead (the target gets the single `work.transferred` one).

Deviations and gaps: Persian text is matched with plain case-insensitive substring only (no Arabic/Persian letter or digit folding except for amounts); calendar recurring reminders show their next occurrence only; the unified search does not scan letter bodies, note bodies or task descriptions; `weekend` is not configurable yet.
